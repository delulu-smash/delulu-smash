# Smash Ultimate Research

The goal is **accurate, Ultimate-only, compact** knowledge that a human can read on the site and an AI can
retrieve cheaply. Most research mistakes in Smash come from **game confusion**: wiki pages and old posts mix
64, Melee, Brawl, Smash 4 and Ultimate.

## Workflow

Full design: `spec/pkgs/ds/ai/knowledge_base.md`. Three layers: SmashDb (numbers), `docs/` (curated
baseline), and `local/staging/` (raw captures, never answered from directly).

1. **Check what already exists.** Grep `docs/` for the topic and its synonyms (page `keywords`,
   `docs/glossary.md`). Update the existing page rather than creating a duplicate. What `docs/` says is the
   baseline everything else gets compared against (see "Using docs/ vs other knowledge").
2. **Capture the raw source into staging.** Save the full source text, not a summary, to `local/staging/`
   (see "Staging" below). Summarizing fetchers drop the game qualifiers that scope filtering depends on. See
   [sources.md](sources.md) for how to fetch each source, eg SmashWiki raw wikitext. If the user pasted
   text, stage it as-is. If the source is already staged, start from that file.
3. **Scope-filter to Ultimate** using the rules below. Keep a sentence only if it applies to Ultimate.
4. **Extract atomic claims:** numbers, rules and exceptions. Tag each one with its source, and note the
   source's own citation if it has one (eg "wiki cites a datamine tweet").
5. **Cross-check** numbers against `docs/`, SmashDb (`ds.ai.smashdb` / `pkgs/ds/data`) or a second source
   when you can. If sources conflict, record both claims and who says what. Never silently pick one. If the
   conflict is with `docs/`, report it as a discrepancy and don't overwrite `docs/` without the user's OK.
   Log every conflict or unverified claim in the register (see "Discrepancies") and continue with the
   provisional value.
6. **Write or update the page** following the `docs-writing` skill. Keep the source's facts separate from
   your own interpretations.
7. **Document sources** using the docs-writing standard (see "Sources (required standard)"). Every research
   pass must leave a collapsed Sources dropdown plus `% research:` lines. Never skip this step, even for
   small edits. For every staged file used, add `% research: staged: <repo-relative path> (machine-local)`
   directly under that source's line, so it can be opened straight from the page.
8. **Update the glossary.** Add every new term or alias to `docs/glossary.md`, with a link to the page.
9. **Add eval cases.** Add 3–8 question/expected-answer cases to `pkgs/ds/ai/evals/smash_knowledge.yaml`
   for the new facts. Include at least one game-confusion trap if the source mixed games. Don't run
   `ds ai eval` unless the user asks, since it calls a paid API.
10. **Mark the staged file processed.** Set `status: processed` and `processed_into: [docs paths]`. Use
    `status: discarded` with a reason in `notes` if nothing was worth keeping.
11. **Report back:** what you kept, what you dropped as out of scope, and anything unverified or conflicting.

## Discrepancies (`docs/scratch/discrepancies.md`)

When sources conflict, or a claim is single-source or derived and needs checking, **log it and keep going**.
Never block the current task waiting on the user.

1. **Pick a provisional value** with these defaults, in order:
   - `docs/` (user-reviewed) wins
   - datamined current-patch data (SmashDb / ultimateframedata) beats community sheets and posts
   - a sourced mechanic rule (eg SmashWiki) beats numbers derived from someone's spreadsheet
   - otherwise take the more conservative value, and say which
2. **Add an entry** to `docs/scratch/discrepancies.md` using the next unused `D-###`, following the format and
   conventions at the top of that file: Affects, Claims (value + source + date), Why they might differ, To
   settle, Provisional, Resolution. In **To settle**, give a concrete test with the expected reading for each
   claim, and reuse the file's "Lab basics" setup instead of repeating it.
3. **Add a pointer line** `% research: discrepancy D-### (<status>) -- docs/scratch/discrepancies.md` to each
   affected docs page.
4. **Use the provisional value** in the work. When an answer depends on it, mention the ID (eg "12% per SmashDb,
   see D-001").
5. **Finish with one line** listing new IDs, eg "logged D-008, D-009 for later".

**"Resolve D-###" / "review discrepancies":**
- Read the entry, the user's `Notes (you):` bullets, and any linked `docs/scratch/lab/*.md` notes (these are
  first-class `Lab:` sources).
- Update the docs under **Affects** first. Then, for each changed page, update the code that cites it
  (`grep -rn "docs-source: docs/<page>.md" pkgs tests`, and the page's `% research: code:` lines), and run
  `uv run pytest tests/`. Code never carries discrepancy tags.
- Fill in **Resolution** with the date, the decision and the evidence.
- Set the status and update the page pointers.
- Add an eval case if the AI could get it wrong again.
- For a review session, group open `needs-lab` entries into one training-mode plan.

## Staging (`local/staging/`)

Raw captures live here. It's git-ignored and machine-local by choice: Discord messages are other people's
words, and the repo may be public.

- **Path:** `local/staging/<kind>/<YYYY-MM-DD>_<source>_<slug>.md`, where `<kind>` is `wiki`, `discord`,
  `twitter`, `video`, `sheets` (spreadsheet tabs as CSV) or `notes`. Eg `local/staging/wiki/2026-09-29_ssbwiki_stale-moves.md`.
- **Content:** YAML frontmatter, then the raw content untouched (no cleanup, no summarizing):

  ```yaml
  ---
  source: SmashWiki            # or "Mac Nation Discord #mac-labs", "@labber on X", ...
  title: Stale Moves
  url: https://www.ssbwiki.com/Stale_Moves
  author:                      # Discord/Twitter/video: who said it
  version: revid=2039011       # if the source has versions
  captured: 2026-09-29
  status: unprocessed          # unprocessed | processed | discarded
  processed_into: []           # docs paths, once processed
  notes:
  ---
  ```
- **"Process staging":** when the user asks this, handle every `status: unprocessed` file through steps 3–10.
  Batch related files into one pass.
- **Not a knowledge source:** don't answer questions from staging. Only curated `docs/` counts.
- **Different folder:** `local/assets/staging` is for media assets, not research.

## Scope filtering rules (multi-game sources)

| Source wording | Keep for Ultimate? |
|---|---|
| "in all games", no game qualifier on a series-wide page | Keep, unless a later Ultimate-specific section overrides it |
| "starting in Melee", "from Brawl onward", "Smash 4 onward" | Keep. The range includes Ultimate. |
| "in Ultimate", `{{SSBU\|...}}`, "Specifics in Ultimate" | Keep. Wins over any general statement. |
| "unchanged from SSB4", "as in Smash 4" (inside an Ultimate section) | Keep **and** pull the referenced Smash 4 behavior in, marked as inherited |
| "prior to SSB4", "until Brawl", "except in Ultimate" | Drop |
| "in Melee/Brawl/Smash 4" only | Drop, unless an Ultimate section says "as in <game>" (eg Ultimate transformations work "as in Melee") |
| Series comparisons, controversy, history | Drop, except a one-line contrast if it prevents a common misconception |

Also:
- **Later statements override earlier ones.** Ultimate sections often revise a general rule (eg items).
  Resolve these before writing.
- **"Super Smash Bros." is ambiguous: it can mean the whole series or the N64 game (Smash 64).** Use context
  to decide:
  - A section or table heading that names one game among others (eg `===''[[Super Smash Bros.]]''===` next to
    Melee/Brawl/Ultimate headings) is usually the N64 game.
  - Wording like "the series", "all games", or wikitext `{{b|Super Smash Bros.|series}}` means the series.
  - Otherwise read the surrounding paragraph for which games it compares.

  Before using a number, check which game's section, table or paragraph it sits in, not just that it matched
  a keyword. Eg the Short hop page's 0.85× short-hop-attack modifier is in the Ultimate paragraph of
  "Mechanics", but a `0.85` also appears in the N64 "Short hop heights" table.
- **Watch for Ultimate-only content** mentioned in passing, such as DLC characters (Kazuya, Pyra/Mythra, Steve)
  or Training Mode toggles.
- **Numbers from Smash 4 are wrong for Ultimate** unless the source says they're unchanged. This is especially
  common in old Smashboards posts and YouTube videos from 2014–2018.
- **Patch sensitivity:** balance changes in Ultimate ran through patch 13.0.x. Note the patch when a claim
  depends on character values. Engine mechanics rarely changed.

## Using docs/ vs other knowledge

The user reviews and verifies `docs/`, but they're still learning, so `docs/` can be incomplete or wrong. Treat
it as the **baseline**: it's the default answer, and other knowledge adds to it or challenges it, never
silently overrides it.

| Situation | What to do |
|---|---|
| `docs/` covers it, nothing disagrees | Answer from `docs/` and cite `docs/<page>.md:line` |
| `docs/` covers it, but general knowledge or a source disagrees | Lead with `docs/`, then add a **Discrepancy** note (format below) |
| `docs/` is silent | Answer from general knowledge or research. Label it "not in docs/", give a confidence level, and offer to add it |
| `docs/` claim is marked unverified (`% research: unverified`, nearby TODO) | Treat it as weaker, and say so if another source disagrees |
| You're unsure of your own general knowledge | Say so, especially for exact numbers (frame data, KO %). Don't present guesses as facts |

**Discrepancy note format** (in chat, not in the page):

```markdown
> **Discrepancy:** `docs/mechanics/stale_moves.md:31` says X.
> <General knowledge | SmashWiki (link) | SmashDb> says Y.
> Confidence: docs/ (sourced, unverified datamine) vs Y (<why>).
> To settle: <lab setup, eg "Training Mode, stale moves ON, 9× fair on shield vs on hit, compare damage">.
```

- **Don't edit `docs/` to fix a discrepancy** unless the user asks. If they confirm, update the page and record
  the resolution in a `% research:` line.
- **Common false discrepancies:** check that the "other" knowledge isn't really about Smash 4, Melee or Brawl,
  or from before a patch, before flagging it.

## Source trust (highest first)

`docs/` (user-verified) is the baseline above this list. Rank sources below it like this when they disagree
with each other:


1. Datamined values: SmashDb, ultimateframedata, datamine spreadsheets, datamine tweets.
2. Your own lab results in training mode. Write down the setup (character, %, stale moves on/off, DI).
3. SmashWiki `(SSBU)` pages and general pages with Ultimate sections. Note what they cite.
4. Character Discords and known labbers on Twitter/X. Good for tech and matchup knowledge, but often not
   precise.
5. General community posts, Reddit and YouTube comments. Use these as leads to verify, never as facts.

## Page format (`docs/`)

Follow the `docs-writing` skill (`.agents/skills/docs-writing/SKILL.md`) for all formatting and page
structure. Research-specific additions:

- Put every community synonym and shorthand for the topic into the frontmatter `keywords`.
- Sources follow the docs-writing "Sources (required standard)" section exactly. The research-specific parts:
  - **Record the source version** in `% research:`. For SmashWiki, that's the `revid` from
    `api.php?action=query&prop=revisions&titles=<Page>&rvprop=ids|timestamp&format=json`.
  - **Record what you kept, dropped, inherited and resolved** during scope filtering.
  - **When updating a page, read its `% research:` lines first** to see which source version was used. For a
    wiki, diff old vs new with `api.php?action=compare&fromrev=<old>&torev=<new>`.

## Condensing

- Keep: rules, numbers, exceptions, interactions, and how to test the mechanic in training mode.
- Drop: history, other-game behavior, controversy, image captions, and wiki meta text.
- Aim for about 1/3 of the source's length or less. Keep tables when there are more than 3 numbers.
