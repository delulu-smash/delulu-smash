# portability: OS + terminal emulator agnosticism

No feature should silently misbehave depending on the user's OS or terminal
emulator. Where true agnosticism is impossible (some things genuinely aren't —
see fonts/clipboard below), degrade to a documented, working fallback instead
of breaking.

## keybindings

Requirements for any new binding:

- Must work in a plain terminal in cbreak/raw mode — don't assume an enhanced
  keyboard protocol (Kitty keyboard protocol / CSI u) unless a fallback is
  also provided, matching the existing `Ctrl+Enter` (needs the enhanced
  protocol; supported by Kitty, iTerm2, WezTerm, Ghostty) / `F5` (works
  everywhere) pair.
- Must not collide with a key the OS or the user's shell already owns.
- Should be verified in at least: macOS Terminal.app, iTerm2, and one
  non-macOS terminal (or VSCode's integrated terminal) before being called
  done.

Known conflicts / gotchas (running list — add to this as we find more):

- **`Tab` / `Shift+Tab`** are claimed by Textual's own `Screen` default
  bindings (`focus_next` / `focus_previous`, see `screen.py`). A widget's
  bindings resolve before the App's, so an App-level binding on either key
  gets silently shadowed rather than erroring — it looks like the key "does
  nothing" for your action. Don't reuse these for app-level actions.
- **`Ctrl+Tab`** is commonly intercepted by terminal emulators and
  multiplexers (tmux, browser-embedded terminals, etc.) for their own tab
  switching, before the keypress ever reaches the app.
- **`Alt`/`Option` combos** depend on the terminal's meta-key setting
  (Terminal.app: "Use Option as Meta Key"; iTerm2: profile's Option key set
  to "Esc+" or "Meta") — off by default in some terminals/profiles, in which
  case Option+key just types an accented/special character instead of
  reaching the app as a modified key. Don't rely on these without either
  detecting the fallback or documenting the required setting.
- **`Alt+Tab` specifically**: rejected outright, not just terminal-dependent.
  It's the OS/window-manager-level window switcher on Windows and most Linux
  desktops (GNOME, KDE, i3, ...) — consumed before it ever reaches the
  terminal, regardless of the terminal's own meta-key setting.
- **`Ctrl+M`, `Ctrl+I`, `Ctrl+H`, `Ctrl+[`** are not distinct keys at all in
  raw terminal mode — they *are* the literal bytes for `Enter`, `Tab`,
  `Backspace`, `Escape` respectively. Legacy 7-bit ASCII control codes are
  generated by clearing the top bits of a letter's code, and a handful of
  letters (8=H, 9=I, 10=J, 13=M) happen to land on numbers that terminals
  separately assigned to named keys — coincidence of the encoding, not
  something specific to those letters. Confirmed in Textual's own source
  (`_ansi_sequences.py`): `\r` maps to `Keys.Enter` and a `ControlM` mapping
  for the same byte is commented out entirely, annotated "Identical to
  `'\r'`". Binding one of these means your action fires on every press of
  the real key it's identical to — a hard block, not a portability
  trade-off. (`Ctrl+J` is *not* in this family — see below, it gets its own
  distinct byte, `0x0A`, separate from `Enter`'s `0x0D`.)
- **`Ctrl+/`** collides at the protocol level with `Ctrl+_`/`Ctrl+-` in a
  plain terminal — all three send the same byte (`0x1F`). Textual has no
  separate `ctrl+slash` identity; its table only names this byte
  `ctrl+underscore`. Only becomes a genuinely distinct keypress under an
  enhanced keyboard protocol (Kitty/CSI-u), same fragility class as
  `Ctrl+Enter`. Also a convention clash even where it works: `Ctrl+/` is
  near-universally "toggle line comment" in code editors, and the same
  underlying byte is "undo" in Emacs/readline (and in this repo's own Claude
  Code, which binds `ctrl+_`/`ctrl+-` to `chat:undo`) — repurposing it fights
  two established mental models at once.
- **`Ctrl+,`** produces no distinguishable byte at all in a plain terminal —
  comma isn't in the C0 control-code range (only letters plus `@ [ \ ] ^ _
  ?` are), so most terminals just send the bare `,` or drop it. Only
  reachable as a real modified key under an enhanced protocol, and unlike
  `Ctrl+Enter` there's no documented universal fallback for it. Also
  contested by convention: `,` means "Preferences/Settings" nearly
  everywhere (VSCode's `Ctrl+,`/`Cmd+,`, macOS's own `Cmd+,` convention).
- **`Ctrl+Space`** is fine at the protocol layer — it sends NUL (`0x00`),
  and Textual explicitly supports it (`keys.py` aliases `"ctrl+space"` to
  `"ctrl+at"`; that byte isn't used for anything else in this app). The
  blocker is macOS itself: `Ctrl+Space` is the default system-wide shortcut
  for "Select the previous input source" (System Settings → Keyboard →
  Keyboard Shortcuts → Input Sources), consumed by the OS before Terminal.app
  /iTerm2/VSCode ever see it, on any Mac with more than one input source
  configured — common, and a direct hit given our MacBook Pro baseline.
- Plain `Ctrl+<letter>` combos not already used by the shell (`Ctrl+C`,
  `Ctrl+D`, `Ctrl+Z`, ...) have been the most reliable choice so far —
  `Ctrl+N`, `Ctrl+Q` work everywhere we've tested with zero caveats;
  `Ctrl+J` (current `cycle_mode` binding — cycles a cell python → shell →
  sql → python, one keybinding regardless of how many modes exist) works
  everywhere except Windows/Linux inside VSCode's integrated terminal (see
  the platform-conditional note above) — accepted knowingly, not
  overlooked.

### host apps that embed a terminal (VSCode, etc.)

A fourth layer on top of OS/WM and terminal-emulator interception: when the
"terminal" is actually a panel inside a larger editor, that editor has its
own global command keybindings that can swallow a keystroke before it ever
reaches the embedded shell/app — governed in VSCode by the
`terminal.integrated.commandsToSkipShell` setting. Unlike OS/WM-level
reservations, this one has a user-facing escape hatch (the user can remove a
command from that list in their own settings), but the app can't set that on
anyone's behalf, so treat it the same as any other non-universal dependency:
avoid it, or document the workaround.

Confirmed always-intercepted in VSCode regardless of terminal focus (from
VSCode's own `DEFAULT_COMMANDS_TO_SKIP_SHELL`, current as of this writing —
recheck against the running VSCode version if this matters for a decision):

- **Debug commands** — Start/Stop/Restart/Continue/Pause/Step, bound to
  `F5`, `Shift+F5`, `Ctrl+F5`, `F9`-`F11`. **This breaks our own `Ctrl+Enter`
  / `F5` fallback pair specifically inside VSCode's integrated terminal** —
  `F5` never reaches the app there, even though it's documented above as the
  universal fallback. Needs either a third fallback key for VSCode users or
  an explicit documented limitation.
- Command palette (`F1`, `Ctrl+Shift+P`/`Cmd+Shift+P`), quick open (`Ctrl+P`)
- Terminal panel commands: toggle (`` Ctrl+` ``/`` Cmd+` ``), new terminal
  (`Ctrl+Shift+` `` `), find in terminal (`Ctrl+F`/`Cmd+F`)
- Panel/fullscreen/zoom toggles, editor-group focus (`Ctrl+1` through `8`)
- Task commands (`Ctrl+Shift+B` build, etc.)

Not confirmed either way (didn't show up in the source list we checked, but
that list wasn't exhaustively verified against every VSCode version) —
`Ctrl+T` (`workbench.action.showAllSymbols`) in particular should be tested
directly rather than assumed safe.

**Platform-conditional VSCode conflicts** (a distinct case from the
always-intercepted list above — safe on one OS, blocked on another):

- **`Ctrl+J`**: VSCode's "Toggle Panel" is registered as `KeyMod.CtrlCmd |
  KeyCode.KeyJ`, and `CtrlCmd` resolves differently per platform — `Cmd+J` on
  macOS, `Ctrl+J` on Windows/Linux. `togglePanel` is on the intercept list, so
  the practical result is: `Ctrl+J` reaches the app fine in VSCode's
  integrated terminal **on macOS** (our baseline, see `usability.md`), but is
  swallowed to toggle/hide the panel instead **on Windows/Linux**. Verified
  clean everywhere else: distinct protocol identity from `Enter` (see the
  `Ctrl+M` family below), not claimed by `TextArea` or `Screen`, no native
  Terminal.app/iTerm2 conflict (those reserve `Cmd+`, not `Ctrl+`, for their
  own chrome). Any `KeyMod.CtrlCmd`-registered VSCode command is worth
  double-checking this way before assuming a Mac-only test clears it for
  every OS.

## fonts / glyphs

The cell-mode prompt icons (`Cell.PYTHON_ICON` / `Cell.TERMINAL_ICON` /
`Cell.SQL_ICON` in `cell.py`) are Nerd Font glyphs and render as tofu/empty
boxes unless the terminal both has a Nerd Font installed *and* has it
selected as its font — neither of which the app can detect or set. README
documents the install step; the fallback (plain characters or emoji) is a
one-constant-per-mode swap and should stay that easy regardless of how many
modes exist (see `aesthetics.md` for why they're all pulled from the same
icon set in the first place).

## clipboard

Two mechanisms, each covering the gap the other leaves (`cell.py`,
`CopyableDataTable`):

- Native OS clipboard export (dataframe's own `write_clipboard()` /
  `to_clipboard()`) — full data, but local-only, doesn't work over SSH.
- OSC 52 (Textual's `App.copy_to_clipboard`) — works over SSH, but not in
  macOS Terminal.app.

No single mechanism covers both cases, so keep both with the native path
tried first and OSC 52 as fallback, as done today.

## process

When adding a new interactive feature, check whether it depends on a
terminal/OS capability that isn't universal. If so, this file is where that
dependency and its fallback get written down — not just a code comment.
